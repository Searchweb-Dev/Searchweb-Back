## 1. 범위와 현재 근거

Pinned는 로그인 계정의 **원본 폴더 ID를 가리키는 바로가기**다. 루트 CUSTOM과 UNORGANIZED를 포함하고 가상 전체 링크 및 하위 폴더 탐색 추가는 제외한다. 폴더·북마크 이동/복제, 별도 이름 저장, 아이콘/색상·드래그·일괄 고정·신규 정렬·검색 개편은 하지 않는다. 기존 폴더와 임시 상단 항목은 자동 고정하지 않는다.

- 서버 `MemberFolderController.java` 24~113행: `POST /api/folders`(현재 ID만 반환), `GET /me/root`, `GET /{folderId}`, `PUT /{folderId}`, `PUT /{folderId}/move`, `DELETE /{folderId}`. `MemberFolderRequests.Create` 15~28행은 pinned가 없고, `MemberFolderResponses` 9~29행에도 pinned가 없다. 기존 클라이언트와 응답 호환성 점검이 필요하다.
- `MemberFolderServiceImpl.java` 36~76행의 생성은 이미 `@Transactional`이고, 143~175행의 루트 조회는 미분류 lazy 백필(`REQUIRES_NEW`, 303~332행)을 부른다. 383~399행은 존재/삭제/소유자 순으로 검증한다. 261~300행은 폴더·북마크를 논리 삭제하며 UNORGANIZED 삭제는 금지한다. `MemberFolderJpaDao.java` 25~43행에는 비관적 락 및 소유자별 조회가 있다.
- `MemberFolder.java` 28~50행의 ID는 `Long`이지만 `src/main/resources/db/init_postgres.sql` 96~115행의 실제 선언은 `int IDENTITY`, 부모 FK도 `int`다. 고정 설계가 이 기존 불일치를 임의로 변경하지 않으며 실제 운영 스키마는 별도 확인해야 한다. DDL에는 `is_pinned`가 없다. 577~592행에는 소유자 인덱스·활성 UNORGANIZED 유일 인덱스가 있다.
- `CurrentMemberIdArgumentResolver.java` 15~34행은 SecurityContext에서 ID를 읽는다. `FolderErrorCode.java` 10~18행: F001=404, F002=400, `F003`=403(기존 오타 `Foo3`를 2026-10-30 오류 응답 정비에서 수정), F007=409. `GlobalExceptionHandler.java` 17~36행은 비즈니스 오류를 `ApiResponse.fail`로 반환한다. `OwnerCheck`가 구현되어 있다고 가정하지 않는다.
- `frontend/src/app/my-links/page.tsx` 169행은 현재 루트 목록의 앞 5/6개를 Pinned처럼 노출한다. `CreateFolderDialog.tsx` 30행의 로컬 `isPinned=true`는 서버 영속 값이 아니다. `SaveLinkDialog.tsx` 127~130, 447~450행의 `pinnedFolderId`는 임시 첫 타일 배치이며 고정 의사가 아니다. `frontend/package.json` 5~11, 32~44행에는 Jest 스크립트/의존성이 없어 선택된 테스트 도구와 현재 환경 사이에 준비 작업이 필요하다.
- `.github/workflows/deploy-prod.yml` 3~7, 57~84행은 main/dev push 또는 수동 실행 시 이미지 빌드·배포를 트리거한다. 로컬 설계 검토만 수행하며 원격 브랜치 최신 상태는 확인하지 않았다.

## 3. 기술 계약 권장안 (구현 전 검토 대상)

### 3.1 생성·변경 API — Q-01 / PIN-01,03,04,09,11,12

- **선택된 경로:** 기존 `POST /api/folders` 본문에 `pinned`를 추가한다. **권장 형식:** `{"parentFolderId":null,"folderName":"예시","description":null,"pinned":true}`. 구버전 클라이언트의 누락/null은 false로 정규화하되 명시된 값은 boolean만 수용한다. 신규 화면 초기값 OFF. 생성 응답은 기존 `ApiResponse<Long>`의 폴더 ID와 201을 유지하는 호환안을 우선 검토한다. 목록/단건 응답에 `pinned`를 추가해 값 재확인 가능하게 하며, 실제 클라이언트 직렬화 호환성은 구현 전 점검한다.
- **선택된 경로:** `PATCH /api/folders/{id}/pinned`. **권장 형식:** `{"pinned":true}` 또는 `{"pinned":false}` 필수(non-null); `@CurrentMemberId`에서 계정 ID를 취하고 본문 소유자 ID를 신뢰하지 않는다. 성공 200 `ApiResponse<MemberFolderResponses>`(실제 ID·서버 확정 pinned 포함)를 권장하며 형식은 검토 대상이다. 이미 목표값과 같으면 성공하되 반전시키지 않는다. 잘못된 JSON/누락/null은 400으로 거부한다. 기존 `PUT /{id}`의 이름·설명 의미를 고정 갱신에 전용하지 않는다.
- 일반 CUSTOM 생성은 단일 서비스 `@Transactional` 안에서 부모·이름 중복 검증과 pinned 기록을 원자적으로 커밋하고 **커밋 성공 전 201을 보내지 않는다**. 기존 create 시그니처 호출자의 false 기본값을 보존한다. 신규 UI는 일반 CUSTOM 생성과 기존 UNORGANIZED를 구분하고, UNORGANIZED를 `POST` 생성하지 않는다. 현재 lazy 백필(`REQUIRES_NEW`)에서 `is_pinned`는 DB 기본값 false로 독립 커밋되도록 설계한다. 이후 같은 폴더 ID에 별도 PATCH로 true를 요청한다. 백필 뒤 PATCH의 **확정 실패**에는 폴더는 유지·고정 false이며 UI는 즉시 이전 미고정 상태로 롤백하고 에러 토스트를 표시한다(부분 성공을 생성 성공으로 오표시 금지, AC-01c/12a). 타임아웃·응답 유실의 **결과 불명확** 상태는 GET pinned 재조회로 최종 서버값과 UI를 동기화한다(AC-12b). 실제 백필 기본값·경합과 PATCH 실패는 구현 단계의 테스트 DB 통합 검증 대상이다.
- **대안(미채택):** 기존 PUT에 pinned 섞기/토글식 POST/별도 고정 테이블. 선택된 Q-01/02와 충돌하거나 생성 원자성·멱등성이 약해지므로 채택하지 않는다.

### 3.2 서비스·보안·오류 — PIN-04,07~12

- 인증 필터와 `@CurrentMemberId`를 거쳐 변경 전 `getOwnedFolder`와 동일한 소유자·미삭제 검사 사용을 **권장**한다. `findByIdForUpdate`를 활용해 같은 폴더의 고정 갱신·삭제 동시 접근을 직렬화하고, 잠금 후 존재/소유/삭제 및 `parentFolderId == null`, `folderType IN (CUSTOM, UNORGANIZED)`을 검증한다. 잠금 순서와 삭제의 기존 정책을 회귀 확인한다. 다른 계정·세션의 역순 목표값 경합은 마지막 **서버 커밋값**을 재조회해 동기화한다(낙관적 동시성 정책/412는 아직 결정 아님).
- **권장 오류 계약:** 비로그인 401(실제 SecurityConfig 매핑 점검), 없음/논리삭제 404(F001), 타인 소유 403(`F003`), 비대상 하위/가상 ID·누락 값은 400 또는 별도 도메인 코드(코드 충돌 여부 확인). 삭제 금지 F007과 핀 금지를 혼동하지 않는다. 409/412를 일반 반복 목표값에 반환하지 않는다. `ApiResponse.success/fail` 포장 및 `FolderErrorCode` 확장 가능성을 따르되 확정 HTTP 정책이 아니며 401/403/404의 정보 노출 정책은 보안 검토 대상이다. 서버 예외·트랜잭션 실패는 변경 성공으로 응답하지 않는다.
- PIN-07: 고정만 바꾸며 폴더 ID·parent·bookmark 연결·이름을 복제하지 않는다. 원본 이름 변경은 루트/핀 조회 캐시 동시 무효화로, 삭제는 `deleted_at IS NULL` 조회 필터로 처리한다. UNORGANIZED는 고정 가능하지만 기존 이동/삭제 제한은 유지한다.

### 3.3 고정 조회 — Q-01/05, PIN-05~10

- `GET /api/folders/me/pinned`: 서버 인증 계정의 `owner_member_id`와 `is_pinned=true`, `deleted_at IS NULL`, 루트(`parent_folder_id IS NULL`) 및 CUSTOM/UNORGANIZED만 조회해 원본 `member_folder_id`를 반환한다. 응답은 기존 `ApiResponse<List<MemberFolderResponses>>` 확장(`pinned` 필드 포함)을 권장한다. 다른 계정의 파라미터/캐시 키를 혼용하지 않는다. 0개는 성공 빈 배열이며 화면이 이를 **확인한 후에만** 안내 카드를 보여준다. 루트 목록에서도 pinned 필드를 제공해 메뉴 상태 일치시킨다.
- 정렬은 My Folder에서 실제 적용하는 정렬 선택(최근/이름/링크 수)을 **같은 데이터와 비교 규칙**으로 필터링 전 전체 고정 집합에 적용한다. 검색·필터 중에도 Pinned 집합의 상대 순서는 유지한다. 임의 DB 고정 순서를 새로 만들지 않는다. 동률 순서와 미분류 포함 비교는 화면 로직을 따라 검증한다. 목록 조회의 lazy UNORGANIZED 백필이 필요한 계정에서 루트·고정 조회의 데이터 일관성을 검사한다.

### 3.4 DB 증분 적용·호환·복구 — Q-02/07, PIN-02,08,10

- **확정 스키마:** `member_folder.is_pinned BOOLEAN NOT NULL DEFAULT FALSE`. 기존/신규 행의 기본값은 false이며, 기존 null을 false로 백필한 뒤 `SET NOT NULL`한다. 이미 저장된 true를 재실행 시 false로 덮어쓰지 않는다. 예시 단계: 컬럼/기본값 존재 여부 확인 → 누락 시 `ADD COLUMN is_pinned boolean DEFAULT false` → `UPDATE member_folder SET is_pinned = false WHERE is_pinned IS NULL` → `SET NOT NULL`. 실제 DDL·락 영향은 운영 스키마·크기 확인 후 별도 승인으로 적용하며 이 문서는 SQL 실행 지시가 아니다.
- **확정 필수 인덱스:** `CREATE INDEX idx_member_folder_owner_pinned ON member_folder(owner_member_id, is_pinned);`. 재실행 시 존재 여부/정의 확인과 충돌 검출, 기존 owner 인덱스와 쓰기 비용·실행 계획을 검토한다. `WHERE is_pinned = true AND deleted_at IS NULL AND parent_folder_id IS NULL` 부분 인덱스는 필수 복합 인덱스의 **대체가 아닌** 보조 옵션으로 실행 계획을 점검한 후 비교한다. `CONCURRENTLY` 생성 필요성과 트랜잭션 제한/락을 실제 환경에서 확인한다. 별도 고정 테이블은 채택하지 않는다.
- 전개 권장 순서: 테스트 DB/백업 및 현재 타입 확인 → 컬럼·기본값·데이터 검증 → 새/구버전 서버 공존 확인(구버전 INSERT는 DB 기본값, 새 서버는 컬럼 존재 필요) → 서버·클라이언트 변경 → 계정별 조회 및 신규/기존/삭제 검증. `init_postgres.sql`은 신규 환경 초기화용이며 수정만으로 기운영 DB가 변경되지 않는다. 운영 DB·CI는 이번 작업에서 **미변경**.
- 복구: 장애 시 기능 트래픽 중지/이전 애플리케이션으로 복원하되 새로 저장된 true값을 지우지 않는다. 컬럼 제거는 저장값을 소실하므로 기본 롤백이 아니다. 복원·재배포 전 백업/스키마 호환 검증 및 별도 사용자 승인 필요. `int` DDL ↔ JPA `Long` 불일치는 별개 위험으로 운영 적용 전에 확인한다.

### 3.5 화면·결과 불명확·캐시 — Q-03/04/05, PIN-01,03,05,06,08,10~12

- 생성 화면은 Pinned만 Coming soon에서 분리하고 토글 OFF로 초기화(다이얼로그 재오픈도 OFF); 아이콘/색상은 비활성 유지. My Folder의 메뉴는 고정/해제 행동과 열기를 분리하고, Pinned 카드의 해제도 **같은 목표값 PATCH**로 처리한다. 상단 고정 영역은 현재 `slice(0,5/6)`를 대신해 실제 서버 pinned만 표시하며 검색·필터와 독립, 개수 상한 없이 Flex-wrap. 정렬은 3.3절에 따라 전체 고정 집합에 My Folder 기존 비교 규칙을 적용한다. 마지막 해제 뒤 안내 문구는 spec 원문 `자주 찾는 폴더를 고정해보세요 📌`를 유지한다. 앞선 피드백의 `:pushpin:` 표기는 후속 사용자 결정 「저 아이콘유지가맞아」에 따라 문구 변경으로 적용하지 않는다. Designer는 확정 정책을 변경하지 않고 여백/패딩·포커스 링·스피너·반응형 간격 및 접근성을 검토한다.
- v5 UI 반영 결정(2026-10-25): Pinned/My Folder 모두 `...` → Rename → 상태별 Pin/Unpin → Delete 순서의 같은 메뉴를 사용한다. UNORGANIZED의 기존 Delete 금지는 유지한다. 열기 버튼과 메뉴 트리거는 중첩하지 않는 형제 요소이며 아이콘·여백을 포함한 메뉴 전체 행이 클릭 대상이다. Pin은 승인 SVG의 몸체/짧은 침 비율을 그대로 쓰고 Unpin은 같은 도형에 사선을 추가한다. 각 렌더링 인스턴스의 실제 트리거를 anchor로 사용하고 폴더 ID만으로 DOM을 찾지 않는다. 기본 위치는 트리거 왼쪽 좌표에서 오른쪽으로 펼쳐지고 아래쪽 간격 4px이며, 뷰포트를 벗어날 때만 최소 shift한다. 메뉴는 하나만 열리고 Esc/바깥 클릭/다른 메뉴 열기로 닫히며 트리거 포커스 복귀·스크롤/resize 재계산을 제공한다. 계정+폴더별 saving/unknown은 두 영역에서 공유해 메뉴 전환으로 중복 요청이나 미확정 결과 잠금을 우회하지 않는다. 이 단락은 메뉴·아이콘·위치 계약만 갱신하며 API/DB/고정 집합/정렬/생성/실패 정책은 바꾸지 않는다. 실제 브라우저 시각 검증 및 독립 검증 통과를 의미하지 않는다.
- v8 단일 노출 결정(2026-10-28): 고정 폴더는 My Folder에서 숨김(사용자 결정) — Pinned에만 표시하고 Unpin 시 My Folder 기존 정렬상 원래 위치로 돌아온다. 화면 표시 정책만 바꾸며 API/DB/데이터 이동·복제는 없다. 위 3.5절 첫 단락의 "Pinned는 바로가기, My Folder에도 원래 폴더 유지" 표현과 spec 등 다른 문서의 같은 취지 문구는 이 결정으로 화면 표시에 한해 대체되며 일괄 수정하지 않았다.
- Pinned 영역 최대 2행, 초과 시 영역 내부 세로 스크롤 결정(2026-10-28): 개수 상한 없는 Flex-wrap은 유지하고 영역 높이만 카드 2행(카드 높이×2 + 행 간격 8px + 안쪽 여백 4px×2; 기본 80px 카드 176px, drawer 92px 카드 200px)으로 고정해 3행부터는 Pinned 영역 안에서만 스크롤한다. 3행 위치로 Pin되면 영역을 그 카드까지 스크롤하며 이동 애니메이션을 보이고(reduced-motion은 즉시), 영역 스크롤 시 … 메뉴는 버튼을 따라가다 버튼이 보이지 않으면 닫힌다. 화면 표시만 바꾸며 API/DB 변경은 없다.
- 화면 상태 권장: `loading`(빈 카드 확정 금지) → `loaded empty/list` → 폴더별 `saving`(클릭 즉시 버튼 비활성화+스피너) → 성공(응답 서버값 반영) / 확정 실패(이전 값 롤백+에러 토스트) / `unknown`(타임아웃·응답 소실: 성공·실패 단정 금지, `GET /api/folders/me/pinned` 재조회 후 서버값과 동기화 및 안전한 목표값 재시도). UNORGANIZED 백필 성공/PATCH 확정 실패는 폴더는 유지하되 미고정 UI로 즉시 롤백+토스트한다. unknown에서 자동 단순 롤백으로 종료하지 않는다. 요청 역전은 폴더별 직렬화/요청 세대 표시로 오래된 응답 무시; 다른 탭/기기 경합은 최종 서버값으로 재조회. 무한 재시도 대신 오류 안내와 수동 재시도 경로를 권장한다.
- React Query 계정별 키로 root/pinned/detail을 분리하고 성공·이름 변경·삭제·고정 변경 시 관련 쿼리 무효화/동일 ID 원본 반영. 로그아웃·계정 전환 시 이전 계정 캐시 제거/접근 차단; 브라우저 로컬 상태를 진실원으로 보지 않는다. CUSTOM 생성 확정 실패 시 닫기/성공 토스트를 보내지 않고, 생성 응답 소실 시 목록/동일 요청 결과의 식별이 가능한지 검토하며 확인되지 않은 재POST로 중복 생성을 단정하지 않는다. UNORGANIZED PATCH 응답 소실 시 3.1절의 GET pinned로 동기화한다.

### 사용자 최종 결정이 실제로 필요한 경우

현재 Q-01~07의 **방향 자체를 재승인받을 항목은 없다.** 위 항목은 기술 검토/PM 운영 확인 우선이며, 기존 제품 정책과 충돌하거나 범위·권한·비용 확대가 밝혀질 때 그 차이만 PM이 대상 문서 버전과 함께 사용자에게 질문한다. 제품 구현 시작·운영 DB 변경·push/머지/배포는 별도 단계 사용자 승인 없이는 불가하다.
